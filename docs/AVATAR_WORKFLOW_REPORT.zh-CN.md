# VRChat 本地素材管理器：改模体验与一键装配改进报告

日期：2026-10-24。基线：1.4.0-preview.3。本报告同时作为本轮改进的设计说明；实际完成情况以末尾实施记录和随包验收记录为准。

## 结论

当前应用已经覆盖“找素材、识别商品、管理文件、导入工程”的大部分入口，但这些入口没有形成连续的改模流程。用户最难的往往不是点击导入，而是确定：该选哪个包、会改哪个工程、是否已经装过、导入和穿上是否都成功、菜单在哪里、出了问题该继续哪一步。

本轮优先补齐连续流程：**改模工作台 → 导入前检查 → 装配并接入菜单 → 分步结果 → 用户效果检查记录**。同一次预制件装配与菜单配置共用一次操作、一次撤销；默认保留作者菜单。跨角色自动变形、任意穿模修复和跨重启自动卸载需要更多工程证据，不能用“自动成功”掩盖未知。

## 研究方法与证据边界

- 依据本项目用户反馈：文件命名混乱、适配版本不明、导入位置未知、MA 窗口术语难懂、误确认后需要撤回、资料库丢失感、反复操作成本高。
- 检查当前源码与现有回归记录：工程导入、MA 助手、工作台入口、Unity 日志、轻量模型预览、AI 和下载收件箱。
- 核对 MA 与 VRChat 官方文档，参考下文来源。
- 本报告不是问卷调查；没有虚构访谈人数、成功率、节省时间或用户满意度。表中的“痛点”是已知反馈或基于流程的产品判断。

| 环节 | 用户遇到的问题 | 应用需要承担的工作 | 优先级 |

| 选素材 | 多适配、多版本、多语言命名 | 展示本地包候选和原路径；不把商品全部适配列表当作本地内容 | P0 |

| 重复操作 | 点两次、换文件名重装、导入成功却误认为失败 | 同工程同内容提醒、执行前复核；继续失败步骤而不是重来 | P0 |
| 安装中 | Unity 编译、重载、弹窗等待，看起来像卡死 | 分别显示文件导入、角色装配、菜单和效果检查阶段 | P0 |

| 多套衣服 | 互相穿插、默认衣服复活、分件混乱 | 角色衣柜、套装互斥、配件组合、身体形态冲突分析 | P1 |
| 更新与卸载 | 卸下一件衣服误删共享依赖，覆盖手动调整 | 稳定对象身份、版本化装配清单、差异检查和选择性恢复 | P1 |

## 容易漏掉的实际问题

| 问题 | 常见结果 | 后续如何处理 |
|---|---|---|
| 着色器缺失或版本不符 | 粉色材质、透明排序异常、光照不一致 | 根据作者依赖声明核对版本；不自动把全部材质替换为通用材质 |
| 身体形态名称不一致 | 衣服宽窄不合、脚部和胸部穿插 | 使用作者提供的 BlendShape 映射与隐藏区域，未知映射不猜 |
| PhysBone、碰撞体、约束 | 裙摆或头发穿入身体，配件跟随错误 | 检查缺失引用、碰撞体范围和动态测试；静止预览不能证明正确 |
| 眼睛、口型、表情和换装动画冲突 | 换衣服时表情失效，旧服装重新出现 | 读取最终控制器与对象绑定，标出同一属性的多个控制者 |
| 根缩放、挂点与坐标 | 道具过大、悬空或偏转 | 保存挂点、局部位置和缩放依据，提供原样撤回；不只看包名 |
| PC 与移动端目标不同 | PC 能用而移动端材质或性能不符 | 先选平台，使用作者对应版本，最终以对应平台构建检查 |
| 商品升级和依赖升级 | 旧版正常，新版引用改变 | 显示版本变化与影响范围；更新前保留工程备份，不后台静默升级整个工程 |
| 场景中多个同名角色 | 套装装到了另一个对象 | 工程路径加稳定场景/对象身份，不能靠名字匹配 |
| 操作被中断 | 重启后不知已经进行到哪一步 | 记录阶段、核对回执、只继续未完成步骤，避免重新导入 |
| 文件与资料库放在不同磁盘 | 盘符断开时以为整理成果丢了 | 保留原记录并提示缺失位置；不偷偷重建空资料库 |

这些是待完善的检查方向，并不表示本版已经具备全套检测。自动化优先处理有明确证据、可恢复的情况；只有选择有歧义或会覆盖用户成果时才打断。效果勾选是可选的个人记录，不强制用户每次导入多点三次。

## 重要设计约束

### 1. 从工程开始，逐步走向角色工作台

本轮工作台集中目标工程、依赖线索、导入记录和下一步操作。它不声称能离线知道 Unity 当前打开的角色。后续角色档案应绑定工程、场景和稳定对象标识；不能只记角色名称，也不能因为只有一个预制件就推断其适配正确。

### 2. 菜单、形态与动画需要共同检查

单个 VRChat 菜单最多 8 个控件，MA 支持满页自动分页。同步参数有总预算；同名参数、默认状态、保存状态、其他玩家的同步效果都可能影响可用性。[1][2][3]

完整衣柜要区分套装互斥和配件叠加。不能把所有服装都强制互斥，也不能把已有作者菜单丢弃再重建。多个动画控制同一对象、多个 Shape Changer 控制同一身体形态时，可能发生覆盖。层级末尾放置还可能改变 MA 同优先级动画的合并顺序，因此“在底部”只是展示与组织规则，不是兼容性证明。[4][5]

本轮采用保守且可用的接入方式：已有 MA 菜单组件则保留；没有时，在用户勾选后创建独立显隐开关。不开启旧衣服自动关闭、套装互斥和身体形态猜测。这些需要角色关系证据后再自动化。

### 3. 自动适配应有证据等级

- 作者适配版本与完整 MA 预设：优先使用原配置。
- 同角色骨骼兼容但无完整预设：使用 MA 装配，效果仍需动作与体型检查。
- 挂件：使用明确挂点及偏移；不按衣服处理。
- 跨角色衣装或未知骨骼：转辅助配置，不因名称相似自动变形。

MA 官方区分可兼容装配的衣装和预先设置好菜单、形态同步、身体遮挡的完整预设。[6] 轻量预览负责看模型；实际 Unity 构建和游戏内同步仍需对应环境验证。

### 4. 成功必须拆开显示

“文件已导入”“角色已装配”“菜单已保留或生成”“用户已检查效果”“SDK 构建通过”分别是不同证据。本轮不增加虚假的 SDK 成功状态；用户手动勾选也不会变成机器验证通过。

### 5. 恢复能力必须保留后来做的修改

即时失败回滚与 Unity Undo 解决当前操作；跨重启恢复需要记录每个修改前后值，并在恢复前比较用户是否又改过。共享材质、着色器、其他角色引用不能按“属于同一次导入”直接删除。后续卸载默认先解除本工具管理的场景配置，文件清理需单独列出实际引用证据。

### 6. 性能要检查最终成品

关闭衣服开关不等于从性能统计中移除。VRChat 性能统计包含禁用对象和组件。[7] 后续应区分“仅构建当前穿搭”和“保留多套游戏内切换”，并显示最终构建后的增量；本轮不以包文件大小推断 FPS 或性能等级。

## 本轮实施范围

1. 新增独立“改模工作台”，集中工程选择、依赖线索、文件与商品入口、导入历史、错误诊断及插件入口；记住选中的工程。
2. 导入预览增加结构化检查和同工程同内容 Unitypackage 重复提示；重新导入必须显式选择，GUID 冲突仍不可覆盖。执行时复核，防止两个旧预览绕过提醒。
3. MA 装配可同时接入菜单：保留作者现有菜单，没有时创建显隐开关；保持预制件直接位于角色末尾，配置合并到同一次 Undo，失败回滚。
4. 显示分步结果和下一步操作；保存外观、动作、菜单的用户检查记录，重启可读。历史记录分页显示，不只展示最近八条。
5. 报告、使用步骤、真实应用截图、测试记录和 Windows 本地预览包一起交付。新增文案先使用中文。

## 社区与 AI 的分工

社区贡献可验证的装配配置，记录商品/角色版本、预制件、依赖、挂点、菜单和已测试动作，保留贡献者署名。配置只描述操作，不夹带原作者的收费素材。AI 负责理解需求、整理检索词、解释说明和诊断建议；工程写入由确定的规则执行和校验，不直接执行 AI 生成的任意脚本。

## 验收标准

- 原素材清单及抽样哈希前后不变；所有 Unity 测试只用独立合成工程。
- 不同工程、包改名但内容相同、同包再次导入、过期预览、GUID 冲突有明确行为。
- 包声明与实际文件分开显示；未知不显示为已安装或兼容。
- 装配与菜单模式覆盖：无菜单、作者自带菜单、多个预制件、菜单配置失败、重复请求与一次撤销。
- 工作台覆盖空工程、失效工程、等待 Unity、导入完成但 MA 失败、人工检查与重启保存。
- 四主题、980px 与 200% 缩放下主要操作可达；截图为实际应用窗口。
- 商业角色适配、真实收费 AI、游戏内最终同步未测时如实记录，不以模拟测试替代。

## 实施记录

本轮已实现 1.4.0-preview.4 的五项范围：改模工作台、结构化导入检查、Unitypackage 内容去重、MA 装配菜单联动和持久化用户检查。代码已通过 877 项回归；隔离 Electron 完成 10 组验收，覆盖四主题、980px/200%、选择工程、菜单请求、重复导入、诊断衔接及重启保存。

真实 Unity 2022.3 编辑器在独立合成工程中执行 62 项断言，包括装配、菜单保留/生成、失败回滚、一次撤销、重启与原生包导入回调。MA 接口使用明确标记的测试替身；不能据此宣称全部真实 MA/SDK 版本兼容或商业角色试穿成功。图文说明中的回执为 UI 合成样例。

独立审查发现并修正：慢初始化覆盖用户新选择、再次选择同一工程使记录空白、复制元数据误当内容摘要。普通复制继续沿用 GUID 冲突检查，内容去重明确限定 Unitypackage。

实际打包后的启动、持久化和资源检查结果见随包《验收记录》。原素材与用户真实工程未用于写入测试。角色衣柜、体型映射、最终构建预算、跨重启卸载、跨角色适配和穿模修复仍未标记完成。
